# Поэтапный план разработки — AI Job Finder & CV Assistant Bot

Это не техзадание заново и не готовый код. Это **разбивка большого проекта на маленькие управляемые этапы**, чтобы не пытаться удержать всё в голове сразу. Каждый этап — это то, что реально сделать за 1-3 дня, закоммитить и получить рабочий результат.

Принцип простой: **на каждом этапе бот должен запускаться и хоть что-то делать.** Не бывает "пишу код 2 недели, потом первый раз запускаю".

---

## Этап 0 — Подготовка окружения

**Цель:** пустой, но настроенный проект.

- [ ] Создать репозиторий на GitHub
- [ ] Создать виртуальное окружение (venv)
- [ ] Установить aiogram, python-dotenv
- [ ] Создать `.env` и `.gitignore` (сразу, до первого коммита с кодом!)
- [ ] Получить токен бота у @BotFather
- [ ] Написать `main.py`, который просто запускает бота и отвечает "pong" на любое сообщение

**Коммит:** `Initialize aiogram project`

**Проверка себя:** бот отвечает в Telegram хоть чем-то → этап закрыт.

## Этап 1 — Роли и старт

**Цель:** бот различает, кто с ним говорит — кандидат или работодатель.

- [ ] Команда `/start` показывает выбор роли (Reply Keyboard: "Я кандидат" / "Я работодатель")
- [ ] Сохранить выбор роли пользователя (пока можно просто в памяти, БД подключим на следующем этапе)
- [ ] В зависимости от роли показывать разное меню

**Коммит:** `Add role selection on start`

**Проверка себя:** можно выбрать роль, и меню меняется.

## Этап 2 — PostgreSQL: минимальная схема

**Цель:** данные не пропадают при перезапуске бота.

- [ ] Установить и настроить PostgreSQL (локально или в Docker)

- [ ] Написать функции: создать пользователя, найти пользователя по telegram_id
- [ ] Подключить бота к БД: при `/start` записывать пользователя, если его ещё нет

**Коммит:** `Add PostgreSQL connection and users table`

**Проверка себя:** перезапустил бота — данные о пользователе остались в БД (проверить через psql/DBeaver).

> Не пытайся сразу создать все 15 таблиц из ТЗ. Добавляй таблицу тогда, когда она реально нужна для текущего этапа.

## Этап 3 — Профиль кандидата (FSM)

**Цель:** первый настоящий многошаговый диалог.

- [ ] Создать таблицу `candidate_profiles`
- [ ] Реализовать FSM-сценарий:
  ```
  Имя → Город → Желаемая должность → Опыт → Навыки → Зарплата → Подтверждение
  ```
- [ ] На каждом шаге сохранять данные через `update_data()`
- [ ] В конце — показать всё, что ввёл пользователь, и сохранить в БД через `get_data()`
- [ ] Добавить возможность отредактировать профиль позже (можно просто заново пройти FSM)

**Коммит:** `Implement candidate profile FSM`

**Проверка себя:** прошёл диалог до конца → в таблице `candidate_profiles` появилась строка.

## Этап 4 — Профиль компании и вакансии (без AI)

**Цель:** та же логика FSM, но для работодателя — закрепляем навык, не изобретаем новое.

- [ ] Таблицы `employer_profiles`, `companies`, `vacancies`
- [ ] FSM для создания компании (Название → Отрасль → Город → Описание)
- [ ] FSM для создания вакансии (Название → Описание → Город → Опыт → Навыки → Зарплата)
- [ ] Простой список "Мои вакансии" для работодателя (без поиска пока)

**Коммит:** `Add employer and vacancy creation flow`

**Проверка себя:** работодатель может создать вакансию, и она видна в списке "Мои вакансии".

## Этап 5 — Поиск вакансий (без AI, без матчинга)

**Цель:** кандидат видит вакансии из БД.

- [ ] Простой запрос SELECT всех активных вакансий
- [ ] Показ списком с Inline-кнопками (Просмотр / Сохранить / Откликнуться)
- [ ] Пагинация (даже простая — "следующие 5")
- [ ] Один фильтр для начала (например, по городу) — остальные фильтры добавить позже

**Коммит:** `Add job search and pagination`

**Проверка себя:** кандидат видит список вакансий и может листать страницы.

## Этап 6 — Отклики на вакансии

**Цель:** связать кандидата и вакансию через таблицу `applications`.

- [ ] Таблица `applications` (candidate_id, vacancy_id, status, created_at)
- [ ] Кнопка "Откликнуться" → создаёт запись со статусом `submitted`
- [ ] Защита от повторного отклика (проверка перед INSERT или UNIQUE constraint)
- [ ] "Мои отклики" для кандидата — список с статусами
- [ ] Работодатель видит список откликнувшихся на его вакансию + может менять статус

**Коммит:** `Implement job applications and status tracking`

**Проверка себя:** повторный отклик на ту же вакансию не создаёт вторую запись.

## Этап 12 — Матчинг кандидат ↔ вакансия (своя логика, не AI)

**Цель:** самое важное для защиты — простая и объяснимая формула.

Пример логики (не копируй как готовый код, это концепция):
```
match_score = 
    (пересечение навыков кандидата и вакансии) * вес_навыков +
    (совпадение уровня опыта) * вес_опыта +
    (зарплата кандидата попадает в диапазон вакансии) * вес_зарплаты +
    (совпадение города) * вес_города
```
- [ ] Реализовать функцию `calculate_match(candidate, vacancy) -> int`
- [ ] Показывать процент соответствия рядом с вакансией
- [ ] Проверить на 2-3 реальных примерах вручную — цифры должны быть логичными

**Коммит:** `Create job matching service`

**Проверка себя:** ты можешь на пальцах объяснить, почему получилось именно 84%, а не другое число.

Если можешь ответить сам себе — на защите тоже ответишь.

## Главное правило

Не пытайся понять весь проект целиком до того, как начать. Пойми **только текущий этап**. Каждый следующий этап опирается на предыдущий и почти всегда переиспользует уже знакомые паттерны:

- FSM повторяется 3 раза (профиль, вакансия, собеседование) — во второй и третий раз будет уже легко.
- AI-вызов один и тот же механизм, просто разные промпты (Этапы 9-11, 13-15).
- Таблицы "многие ко многим" повторяются (отклики, сохранённые, навыки-кандидата, навыки-вакансии).

Два месяца бэкенда — достаточно, чтобы пройти это по шагам. Недостаточно было бы, чтобы написать это всё за один присест без плана — но план у тебя теперь есть.
